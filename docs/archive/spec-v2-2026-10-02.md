# Đặc tả app quản lý Sales: bản Desktop (Java + JavaFX)

Phiên bản: v2, ngày 02/10/2026. Thay thế bản v1 (web + mobile).

## 1. Mục tiêu
Gom toàn bộ công việc của một Sales Manager vào **một app desktop duy nhất**, thay cho nhiều file Excel rời rạc:
- Theo dõi **doanh số, công nợ, tiến độ chỉ tiêu** trực quan, không cần ghi chú thủ công
- Quản lý khách hàng và lịch viếng thăm
- Theo dõi khuyến mãi công ty đang chạy và tiến độ của từng khách
- Theo dõi tồn kho, hạn dùng để có chính sách đẩy hàng
- **Xuất báo cáo khi cần**, không phải lưu file rời

Người dùng: **một mình bạn**. Dùng thật trong công việc.

## 2. Nguyên tắc thiết kế
1. Dữ liệu gốc (đơn hàng, hóa đơn, công nợ, tồn kho) nằm ở công ty. App **đọc và tổng hợp**, không thay thế hệ thống công ty.
2. Nhập dữ liệu chủ yếu bằng **import Excel**. Chỉ nhập tay những thứ công ty không có: viếng thăm, ghi chú, chỉ tiêu cá nhân, ảnh trưng bày, ấn phẩm marketing đã cấp.
3. Một người dùng nên **không cần phân quyền, không cần server riêng, không cần đăng nhập**. Dữ liệu nằm trên máy bạn nên cần **mã hóa ổ đĩa** (BitLocker/FileVault) và **backup tự động**.
4. Mọi con số tiền được tính bằng `BigDecimal`, tuyệt đối không dùng `double`.
5. Làm từng giai đoạn nhỏ, mỗi giai đoạn dùng được ngay.

### 3.1 Giao diện đẹp (UI)

JavaFX mặc định trông cũ, nhưng chỉnh được khá nhiều bằng thư viện và CSS.

| Mục đích | Công cụ | Ghi chú |
|---|---|---|
| Giao diện hiện đại | **AtlantaFX** | Bộ theme sáng/tối kiểu hiện đại (Primer, Nord, Cupertino...), cài một dòng là cả app đổi diện mạo; dễ chỉnh thêm bằng CSS |
| Biểu tượng | **Ikonli** (Material Design Icons, FontAwesome...) | Icon vector sắc nét cho menu, nút bấm |
| Dựng màn hình | **Scene Builder** + FXML | Kéo thả, tách giao diện khỏi code |
| Thành phần bổ sung | **ControlsFX** | Lọc bảng, thông báo, hộp thoại đẹp hơn |
| Thẻ số liệu (KPI card) | **TilesFX** hoặc tự dựng bằng CSS | Hợp cho dashboard |
| Biểu đồ cơ bản | JavaFX Charts + CSS | Đủ cho cột, đường, tròn |
| Biểu đồ đẹp, tương tác | **WebView + Apache ECharts** | Xem bên dưới |
| Tùy biến | CSS riêng (`styles.css`) | Màu thương hiệu, cỡ chữ, khoảng cách |

**WebView là gì và dùng thế nào:**
`WebView` là thành phần có sẵn của JavaFX, hiển thị trang HTML/CSS/JS ngay trong cửa sổ app. Cách dùng hợp lý cho app này là **nhúng riêng phần dashboard** (biểu đồ doanh số, tuổi nợ, cơ cấu nhóm khách) bằng **ECharts** hoặc Chart.js:
- Java truy vấn dữ liệu rồi truyền cho trang HTML dưới dạng JSON (qua `WebEngine.executeScript` hoặc cầu nối `JSObject`).
- Trang HTML chỉ lo hiển thị; mọi tính toán vẫn nằm trong `service` ở Java.
- Có thể dùng lại chính trang HTML đó để **xem trước báo cáo** trước khi xuất PDF.

**Hạn chế của WebView cần biết:**
- Dùng engine WebKit bản cũ nên hỗ trợ JavaScript hiện đại và một số CSS kém hơn trình duyệt thật; phải thử ECharts trên WebView trước khi dựa vào.
- Tốn thêm bộ nhớ và khởi động chậm hơn.
- Phải chuyển dữ liệu qua lại giữa Java và JS, thêm một lớp phải bảo trì.
- Chữ trong WebView nhập liệu không đồng bộ giao diện với phần JavaFX còn lại.

**Khuyến nghị:**
1. **Giai đoạn 1:** dùng **AtlantaFX + Ikonli + JavaFX Charts**. Cách này đủ đẹp, thuần Java, ít rủi ro.
2. **Giai đoạn 2-3:** nếu biểu đồ gốc chưa đủ ý, thêm **một màn hình dashboard dùng WebView + ECharts**. Chỉ dùng WebView cho đúng chỗ cần biểu đồ, không dựng cả app bằng WebView.
3. Cách khác nếu muốn giao diện web hoàn toàn: dùng JCEF (nhúng Chromium) hoặc chuyển sang web app; nhưng nặng và phức tạp hơn nhiều, không cần cho app một người dùng này.

**Nguyên tắc thiết kế giao diện:**
- Một thanh menu bên trái, nội dung bên phải; trang mở đầu là "Việc hôm nay".
- Màu cố định để biểu thị trạng thái: đỏ = quá hạn, cam = sắp đến hạn/cận date, xanh = đạt.
- Bảng dữ liệu luôn có tìm kiếm, lọc, sắp xếp; số tiền căn phải, định dạng 1.234.567.
- Hỗ trợ chế độ sáng/tối (AtlantaFX có sẵn).
- Thao tác nặng (import, báo cáo) chạy nền kèm thanh tiến trình, giao diện không bị đơ.

**Không dùng Spring Boot.** Bạn chưa học Spring, và app desktop một người dùng không cần nó. Dùng Java thuần với phân lớp rõ ràng (mục 4).

**Ghi chú về truy cập DB:** bắt đầu bằng **JDBC thuần + Repository tự viết** để hiểu rõ SQL (các báo cáo doanh số, công nợ là truy vấn tổng hợp, JDBC/SQL viết thẳng thường dễ hơn ORM). Hibernate chỉ thêm nếu thấy CRUD lặp lại quá nhiều.

**Ghi chú về PostgreSQL trên desktop:** phải cài Postgres trên máy, hơi nặng cho app cá nhân. Hai phương án:
- (a) Cài Postgres thật (khuyến nghị nếu sau này muốn nhiều máy hoặc lên server).
- (b) Dùng **SQLite** (một file duy nhất, không cài đặt, backup chỉ cần chép file). Đơn giản hơn nhiều cho một người dùng, nhưng bạn đã nói muốn Postgres, và kiểu dữ liệu tiền/ngày của SQLite lỏng hơn.

Spec này mặc định (a). Nếu thấy cài đặt phiền, chuyển sang (b) chỉ cần đổi lớp truy cập dữ liệu nếu bạn giữ phân lớp tốt.

## 5. Mô hình dữ liệu

### 5.1 Danh sách bảng
| Nhóm | Bảng |
|---|---|
| Khách hàng | `customer_group`, `customer` |
| Sản phẩm | `product`, `price_tier` (giá theo nhóm khách) |
| Bán hàng | `sales_order`, `order_item`, `invoice` |
| Công nợ | `receivable`, `payment` |
| Tồn kho | `stock_lot` (theo lô: số lô, ngày sản xuất, hạn dùng, số lượng) |
| Khuyến mãi | `promotion`, `promotion_rule`, `promotion_scope`, `promotion_progress`, `display_check`, `marketing_material_issue` |
| Chỉ tiêu | `kpi_target` (tổng), `customer_target` (từng khách) |
| Công việc | `visit`, `reminder` |
| Hệ thống | `import_batch` (lịch sử import, chống nhập trùng), `app_setting` |

### 5.2 Quy ước chung
- Tiền VND: `NUMERIC(15,0)`; đổi `(15,2)` nếu cần ngoại tệ. Trong Java dùng `BigDecimal`.
- Mã khớp với công ty: `customer.code`, `sales_order.order_no`, `invoice.invoice_no`, `product.sku` đều **UNIQUE**, dùng để import không bị trùng.
- Ngày dùng kiểu `DATE`; thời điểm dùng `TIMESTAMP`.
- Tên người bán lưu dạng chữ (`sales_rep_name`) lấy từ file import, không cần bảng người dùng.

### 5.3 Điểm thiết kế quan trọng
- **Nhóm khách (`customer_group`)** giữ chính sách mặc định: hạn mức nợ, kỳ hạn nợ, số ngày nhắc trước hạn, ngưỡng hạn dùng tối thiểu còn lại. Khách để trống thì lấy theo nhóm.
- **Giá theo nhóm (`price_tier`)**: mỗi sản phẩm có thể có giá khác nhau theo nhóm khách.
- **Công nợ theo hóa đơn:** còn nợ = `amount − paid_amount`; tuổi nợ tính từ `due_date`, không lưu thành cột.
- **Giá vốn (`product.cost_price`) và `order_item.unit_cost`**: lưu giá vốn lúc bán để lãi gộp đơn cũ không đổi khi giá vốn thay đổi.
- **Khuyến mãi** (mục 7) tách thành quy tắc + phạm vi + tiến độ để mô tả được cả 5 dạng.

- Bộ mô phỏng khuyến mãi lãi/lỗ (cần giá vốn): hòa vốn, so với các đợt trước
- Gợi ý khuyến mãi bằng AI (xem mục 9), chỉ làm khi đã có vài tháng dữ liệu

### Ngoài phạm vi (tạm thời)
- **Điện thoại:** bản desktop không có check-in GPS. Viếng thăm ghi tay (ngày, mục đích, kết quả). Nếu sau này cần xem nhanh trên điện thoại, làm thêm một web app chỉ xem, hoặc chuyển Postgres lên server.
- Dùng nhiều máy: dữ liệu nằm trên một máy. Muốn dùng hai máy phải đặt Postgres ở máy chủ/VPS.
- Quản lý kho, xuất hóa đơn: là việc của công ty.

## 7. Khuyến mãi (5 dạng công ty đang chạy)

| Dạng | Cách mô hình hóa |
|---|---|
| Chiết khấu % theo số lượng | `promotion_rule`: bậc thang (từ số lượng A giảm x%, từ B giảm y%), theo sản phẩm |
| Mua X tặng Y | `promotion_rule`: mua `buy_qty` tặng `free_qty`, có thể nhiều mức, theo sản phẩm |
| Thưởng doanh số quý/năm | `promotion_rule`: mốc doanh số theo kỳ + mức thưởng; app tính tiến độ và số còn thiếu |
| Thưởng trưng bày | `display_check`: ngày kiểm tra, ảnh, đạt/không đạt, mức thưởng |
| Ấn phẩm marketing | `marketing_material_issue`: ấn phẩm, số lượng, ngày cấp, khách nhận |

- `promotion`: mã, tên, loại, ngày bắt đầu/kết thúc, ghi chú điều kiện.
- `promotion_scope`: áp dụng cho nhóm khách hoặc từng khách, và danh sách sản phẩm.
- `promotion_progress`: tiến độ **từng khách theo từng chương trình theo từng kỳ** (đã đạt, còn thiếu, đã đủ điều kiện thưởng chưa).
- Việc tính tiến độ chạy trong `service`, có test riêng cho từng dạng.

**Cần bạn cung cấp ví dụ thật cho từng dạng** (mục 11) trước khi chốt cấu trúc bảng quy tắc.

## 9. Quy tắc nghiệp vụ cần chốt
- **Doanh số tính theo ngày đơn hàng hay ngày xuất hóa đơn?** Có trừ hàng trả về không? (theo cách công ty đang tính)
- **Công nợ:** còn nợ = tổng hóa đơn − tổng đã thu; tuổi nợ tính từ ngày đến hạn.
- **Hạn mức và kỳ hạn:** theo nhóm khách, có ngoại lệ từng khách.
- **Chỉ tiêu:** đặt theo tháng, quý, năm; cho tổng và từng khách.
- **Hạn dùng:** cảnh báo khi còn dưới X% hạn; ngưỡng riêng cho từng nhóm (MT thường khắt khe hơn).
- **Nhắc nợ:** nhắc trước hạn N ngày (theo nhóm), và mỗi ngày khi quá hạn.
- **Thiếu chỉ tiêu:** so phần trăm đạt được với phần trăm thời gian đã trôi qua của kỳ.

**Về AI gợi ý khuyến mãi (giai đoạn 3):** gọi Claude API từ app, chỉ gửi **số liệu đã tổng hợp**, không gửi tên khách, số điện thoại hay giá vốn chi tiết. Việc tính tiền vẫn do code làm; AI chỉ đọc kết quả và đề xuất, bạn duyệt rồi kiểm tra lại bằng bộ mô phỏng. Cần mạng và API key (lưu trong cài đặt, không để trong mã nguồn).

## 9.1 Import Excel: yêu cầu chi tiết
1. Chọn loại file (đơn hàng / hóa đơn / công nợ / tồn kho).
2. App đọc bằng Apache POI, **ánh xạ cột** theo cấu hình (lưu lại cho lần sau).
3. Màn hình xem trước: dòng hợp lệ, dòng lỗi (thiếu mã khách, ngày sai, số âm...).
4. Xác nhận thì ghi vào DB trong **một transaction**; lỗi giữa chừng thì hoàn tác toàn bộ.
5. Chống trùng bằng khóa (`order_no`, `invoice_no`, mã khách); import lại cùng file không làm tăng gấp đôi số liệu.
6. Lưu `import_batch` để biết dữ liệu đến từ lần import nào và có thể hủy cả lô.
7. Khách hoặc sản phẩm chưa có trong DB: hỏi tạo mới hoặc bỏ qua.

## 10. Phi chức năng
- **Bảo mật:** mã hóa ổ đĩa; mật khẩu DB không để trong mã nguồn; giá vốn là dữ liệu nhạy cảm.
- **Backup:** tự động `pg_dump` khi đóng app và theo lịch; giữ nhiều bản; thử khôi phục định kỳ. Mất dữ liệu công nợ là rủi ro lớn nhất.
- **Hiệu năng:** đánh index theo (khách, ngày) cho đơn hàng và công nợ; báo cáo chạy ở luồng nền để giao diện không bị đơ (`Task` của JavaFX).
- **Ngôn ngữ giao diện:** tiếng Việt; định dạng tiền theo VND, ngày theo dd/MM/yyyy.
- **Kiểm thử:** test bắt buộc cho công thức tuổi nợ, tính doanh số theo kỳ, tiến độ từng dạng khuyến mãi, và import (trùng, lỗi, hoàn tác).
- **Quyền dữ liệu:** dữ liệu khách hàng, công nợ, giá vốn thuộc về công ty. Cần xác nhận việc dùng trên máy cá nhân có được phép. Khi đưa lên GitHub làm portfolio, chỉ dùng dữ liệu giả.

## 11. Việc cần chuẩn bị trước khi code
1. **Mẫu file Excel thật** (đã xóa tên khách và số liệu nhạy cảm) của: đơn hàng, hóa đơn, công nợ, tồn kho. Phần import phải khớp đúng cấu trúc các file này.
2. Quy tắc tính doanh số của công ty (mục 9).
3. Danh sách nhóm khách và chính sách công nợ của từng nhóm.
4. Một ví dụ cụ thể cho mỗi dạng khuyến mãi ở mục 7.
5. Xác nhận quyền sử dụng dữ liệu công ty.
6. Quyết định Postgres (cài trên máy) hay SQLite (một file) cho DB.
